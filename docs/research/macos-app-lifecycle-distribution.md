# macOS app lifecycle, distribution, and helper boundary

> Historical research from 29 August 2026, preserved during branch consolidation.
> Repository observations and proposed decisions describe the proof of concept at that time; they are not current implementation or support claims. Current deployment follows [paired-host execution](../adr/0001-paired-host-execution.md), which rejects cross-Mac RemotePairing projection. See [current ship status](../SHIP_STATUS.md) and [connection design](../CONNECTION_DESIGN.md). External sources have not been revalidated for this merge.

Research date: 2026-08-29

Context pointer: [Research signed macOS app, helper, and launch-at-login constraints](https://github.com/radeknovis/Debagr/issues/4)

Parent map: [Debagr: Productize persistent multi-device Apple device access over Tailscale](https://github.com/radeknovis/Debagr/issues/1)

Scope: Apple primary documentation plus the current Debagr repository. This note does not change product source code and does not claim that Apple CoreDevice or RemotePairing permits the complete product journey; that is a separate map question.

## Executive recommendation

For the first real product boundary, use one signed, notarized, user-session menu-bar app:

1. Make the main app a status-item app (`LSUIElement = true` plus AppKit `NSStatusItem`). Register the main app with `SMAppService.mainApp` for launch at login on macOS 13 and later. Apple documents `mainApp` specifically for configuring the main application as a login item, and `register()` causes the main application to launch at subsequent logins. ([`LSUIElement`](https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement), [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem), [`SMAppService.mainApp`](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29))
2. Keep the relay controller, Bonjour state, device state, and owned child processes in that user process. Do not add a LaunchAgent or root LaunchDaemon in v1 merely to obtain launch-at-login.
3. Distribute outside the Mac App Store as a Developer ID-signed, Hardened Runtime, notarized artifact. Keep App Sandbox as an explicit compatibility decision: Apple makes it optional for notarized non-App-Store distribution, while the current proof of concept launches fixed external tools and listens on the network; `Process` children inherit a parent app’s sandbox. The smallest defensible first release is therefore non-root and Hardened Runtime, with a follow-up test before enabling App Sandbox. ([Preparing your app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [`Process`](https://developer.apple.com/documentation/foundation/process), [Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution))
4. Preserve explicit ownership for every long-lived subprocess. Stop through its retained `Process` object, use the process identifier only for a narrowly scoped forced fallback, and never use executable-name or global process kills.

This is an inference from the cited Apple constraints and the current repository. It minimizes binaries, IPC, installation steps, authorization prompts, and privilege while still giving the product a persistent user-session process and a visible recovery surface.

## Current repository evidence

- [`Package.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Package.swift) is a SwiftPM executable package with a macOS 13 deployment declaration; it has no app bundle, `Info.plist`, menu-bar target, launch-item declaration, entitlements, signing configuration, or notarization workflow.
- [`README.md`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/README.md) describes a CLI proof of concept. It explicitly says UI, multiple devices, and automatic port/configuration behavior are outside the MVP.
- [`main.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/main.swift) owns the relay/proxy/browser/tunnel lifecycle and stops them in a deliberate order. It also handles `SIGINT`, `SIGTERM`, `SIGHUP`, and `atexit`.
- [`ProcessSupport.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/ProcessSupport.swift) creates `Process` instances with an executable URL and argument array, never a shell command. `OwnedLineProcess` retains the child, calls `terminate()`, and has a PID-scoped `SIGKILL` fallback after a short grace period.
- [`BonjourProxy.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/BonjourProxy.swift) owns a separate `dns-sd` process and applies the same cooperative-then-narrow-forced shutdown pattern.
- [`TunnelPortWatcher.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/TunnelPortWatcher.swift) owns `/usr/bin/log stream`; the application stops that watcher before closing the proxy and relay resources.
- [`DeviceProfile.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/DeviceProfile.swift) persists user-scoped configuration under `~/.config/nuticast-poc`, creating the directory with mode `0700` and the file with mode `0600`. That is suitable evidence for a user-session design, not a reason to introduce a system daemon.

## Model comparison

| Model | Launch/login and background behavior | Signing and installation | Privilege and cleanup | Product fit |
| --- | --- | --- | --- | --- |
| Main menu-bar app | `LSUIElement` hides the app from the Dock while allowing a status item; `SMAppService.mainApp` registers the app for subsequent logins. It runs in the logged-in user’s session, where it can present status and recovery UI. ([`LSUIElement`](https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement), [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem), [`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice)) | One app bundle and one login-item registration. All executable code in the shipped bundle still needs valid signing, and the final distribution needs Developer ID plus notarization. ([Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)) | Runs without root. The app can retain each `Process` handle and stop only children it started. ([`Process`](https://developer.apple.com/documentation/foundation/process), [`terminate()`](https://developer.apple.com/documentation/foundation/process/terminate%28%29)) | Best v1: one process, visible status, minimal interaction, no helper IPC. |
| Main app plus user LaunchAgent | A LaunchAgent runs on behalf of the logged-in user. `SMAppService.agent(plistName:)` expects a plist in `Contents/Library/LaunchAgents`; registration bootstraps it immediately and on later logins. The system can report `enabled`, `requiresApproval`, `notRegistered`, or `notFound`. ([Service Management](https://developer.apple.com/documentation/servicemanagement), [`agent(plistName:)`](https://developer.apple.com/documentation/servicemanagement/smappservice/agent%28plistname%3A%29), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [`SMAppService.Status`](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum)) | Adds a helper executable, a launchd plist, a second target, a signing relationship, and an IPC/control path. Apple’s bundled-service layout avoids hand-installing plists into user or system directories; the executable can live in `Contents/Resources`, with `BundleProgram` in the plist. ([Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos)) | Still user-level, so it is compatible with least privilege. The agent must own and reconcile its children; the UI must not kill arbitrary processes in the agent’s place. ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [Secure Coding Guide: Designing Secure Helpers and Daemons](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/DesigningSecureHelpers/DesigningSecureHelpers.html)) | Keep as the fallback if the product must keep relays alive after the UI quits or must get launchd-supervised crash recovery without requiring a new login. It is not needed just for launch-at-login. |
| Login-item helper app | A helper app can be placed in `Contents/Library/LoginItems` and registered with `SMAppService.loginItem(identifier:)`. A registered LoginItem helper starts immediately and at later logins; Apple documents relaunch after a crash or non-zero exit for this service type. ([Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)) | Requires an additional app bundle nested in the main bundle and another signed target. | User-level, but creates an additional process boundary and IPC contract. `unregister()` terminates a running LoginItem, LaunchAgent, or LaunchDaemon; the main app itself remains running when its own main-app registration is unregistered. ([`unregister()`](https://developer.apple.com/documentation/servicemanagement/SMAppService/unregister%28%29)) | A possible later crash-resilient engine, but larger than the v1 main-app boundary and not needed for a visible menu-bar process. |
| LaunchDaemon / privileged helper | A LaunchDaemon is a system-level background process, may run before users log in, and has no user interface. `SMAppService.daemon(plistName:)` expects a plist in `Contents/Library/LaunchDaemons`; a registered daemon requires administrator approval before bootstrap. ([Service Management](https://developer.apple.com/documentation/servicemanagement), [`daemon(plistName:)`](https://developer.apple.com/documentation/servicemanagement/smappservice/daemon%28plistname%3A%29), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [Designing Daemons and Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/DesigningDaemons.html)) | Adds a system-level plist, approval/install behavior, extra signing surface, and IPC authorization surface. | Apple describes LaunchDaemons as root/system-context services and recommends least privilege: avoid root unless the operation actually requires it, and isolate only the minimum privileged work in a helper. ([Service Management](https://developer.apple.com/documentation/servicemanagement), [Elevating Privileges Safely](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/Articles/AccessControl.html)) | Out of scope for v1. ## Findings by concern

### Launch at login

`SMAppService` is Apple’s current API for controlling LoginItems, LaunchAgents, and LaunchDaemons from an app bundle on macOS 13 and later. `SMAppService.mainApp` represents the main application as a login item; `register()` makes the main app launch on subsequent logins. ([`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice), [`SMAppService.mainApp`](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29))

The app must treat registration as observable state rather than assume success forever. Apple exposes `status`, including `requiresApproval`, and provides `openSystemSettingsLoginItems()` for cases where the user needs to change authorization. This supports a one-time, actionable fallback instead of repeated per-device setup. ([`SMAppService.Status`](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum), [`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice), [Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos))

If the product later uses a LaunchAgent for a user, registration is per user: Apple says an app registering an agent for multiple users must call the API once for each user while that user is running the app. For this product’s personal developer workflow, the initial boundary should be one logged-in user per Mac. ([`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29))

Unpair/uninstall must use the same ownership mechanism. `SMAppService.unregister()` prevents future launches and terminates a running LoginItem, LaunchAgent, or LaunchDaemon; if the service is the main application, the already-running app continues but will not launch at the next login. ([`unregister()`](https://developer.apple.com/documentation/servicemanagement/SMAppService/unregister%28%29))

### Menu-bar and background behavior

`LSUIElement` declares an agent app that runs in the background and does not appear in the Dock. `NSStatusItem` is AppKit’s native object for an item displayed in the system menu bar and supports a menu or button. That combination matches the required low-interaction status/recovery surface. ([`LSUIElement`](https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement), [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem))

`LSBackgroundOnly` instead declares that the app runs only in the background. It is the wrong default for a product that must expose a user-visible status item; use `LSUIElement` and a normal AppKit event loop for the menu-bar app. ([`LSBackgroundOnly`](https://developer.apple.com/documentation/bundleresources/information-property-list/lsbackgroundonly), [`NSStatusItem`](https://developer.apple.com/documentation/appkit/nsstatusitem))

Apple distinguishes a user LaunchAgent from a system LaunchDaemon: agents run on behalf of the currently logged-in user, while daemons run in the system context and cannot present a user interface. The archived Daemons and Services guide also documents that a per-user launchd loads agents at login and sends them `SIGTERM` at logout. ([Service Management](https://developer.apple.com/documentation/servicemanagement), [Designing Daemons and Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/DesigningDaemons.html), [Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html))

The main-app choice has one important limitation: Apple’s `register()` documentation explicitly promises subsequent-login launch for `mainApp`, but explicitly documents crash relaunch for a LoginItem helper, not for the main application. If “recover from an app crash without the next login” is a hard acceptance criterion, create a separate prototype/decision ticket before switching to an agent or helper. ([`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29))

### Signing, notarization, and packaging

For direct distribution, Apple’s notarization guidance requires all distributed executables to have valid code signatures, a Developer ID certificate, Hardened Runtime, a secure timestamp, and no `com.apple.security.get-task-allow` entitlement set to true. Apple’s current distribution guidance makes App Sandbox optional for notarized software distributed outside the Mac App Store. ([Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Preparing your app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Configuring the Hardened Runtime](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime))

Nested executable code must be signed before the outer bundle is signed; Apple’s code-signing guidance records nested code in the outer resource envelope. Standard locations include `Contents/MacOS`, `Contents/Helpers`, `Contents/XPCServices`, `Contents/Library/LoginItems`, and `Contents/Library/LaunchServices`. Apple’s Service Management layout puts LaunchAgent and LaunchDaemon plists in `Contents/Library/LaunchAgents` and `Contents/Library/LaunchDaemons`, with the helper executable referenced using `BundleProgram`. ([TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html), [Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos))

The distribution artifact should therefore be built and signed as a real app bundle, then notarized as the final DMG, ZIP, or installer package. Apple documents `notarytool` and `stapler` for automated/custom workflows and recommends testing the shipped artifact, not only the build output. ([Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow))

The present SwiftPM executable is not yet a distributable app bundle. Converting it into an app target and deciding whether a CLI is embedded or separately shipped is future implementation work, not part of this research ticket.

### Least privilege and App Sandbox

Apple’s secure-coding guidance states the principle of least privilege and recommends avoiding root; if a task truly needs root, isolate only that task in a separate helper and keep the helper as small as possible. The current service model makes a LaunchDaemon a root/system-context boundary, so it should not be introduced for ordinary user-level network relay work. ([Elevating Privileges Safely](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/Articles/AccessControl.html), [Service Management](https://developer.apple.com/documentation/servicemanagement))

App Sandbox is a separate axis from root privilege. Apple says Sandbox is optional for notarized non-App-Store distribution, and Foundation documents that subprocesses created by `Process` inherit the parent app’s sandbox; Apple points to XPC services when a helper needs different sandbox entitlements. ([Preparing your app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [`Process`](https://developer.apple.com/documentation/foundation/process))

The current POC launches `/usr/bin/dns-sd`, `/usr/bin/log`, and an installed Tailscale executable, and creates local TCP/UDP listeners. The repository does not yet prove the exact App Sandbox entitlements and behavior for that combination. Therefore the first private release should keep the process user-level and Hardened Runtime-protected, but leave App Sandbox as a named compatibility follow-up rather than claiming it works. This is a product inference from the repository evidence and Apple’s sandbox inheritance rule.

### Safe owned-process cleanup

Foundation’s `Process` represents a subprocess, exposes its `processIdentifier`, and supports a termination handler. `terminate()` sends `SIGTERM` to the receiver and its subtasks, but Apple notes that termination is not guaranteed if the process ignores the signal. ([`Process`](https://developer.apple.com/documentation/foundation/process), [`processIdentifier`](https://developer.apple.com/documentation/foundation/process/processidentifier), [`terminationHandler`](https://developer.apple.com/documentation/foundation/process/terminationhandler), [`terminate()`](https://developer.apple.com/documentation/foundation/process/terminate%28%29))

The safe product rule is consequently:

- Create one ownership record per child: `Process` object, PID, purpose, target-device identity, launch arguments, and lifecycle generation.
- Stop through the retained `Process` object with cooperative termination first. A forced fallback may use the still-owned PID only after rechecking that same process object remains running and after a short grace period.
- Never use `pkill`, executable-name matching, broad `killall`, or a global launchd kill operation. A target-device disconnect must not terminate another target device’s relay or an unrelated developer process.
- If a LaunchAgent is added, the agent—not the menu-bar app—should own its subprocesses and expose a narrow authenticated control channel for start/stop/status. Unregistering the agent is the service-level action; child cleanup remains the agent’s responsibility.
- Keep the current shutdown ordering: stop log watchers and Bonjour subprocesses first, then close relay listeners. Make startup idempotent so a crash or forced termination does not depend on cleanup having run.

The first four bullets are design rules derived from Apple’s `Process` semantics and the security principle of least privilege; the shutdown-order observation is directly supported by the current repository implementation in [`main.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/main.swift), [`ProcessSupport.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/ProcessSupport.swift), and [`TunnelPortWatcher.swift`](https://github.com/radeknovis/Debagr/blob/a3e6374749345051f21e5e217fff474d9095e1db/Sources/NuticastPOC/TunnelPortWatcher.swift).

## Smallest defensible product boundary

### Include in v1

- One AppKit menu-bar app, with `LSUIElement` and an `NSStatusItem`.
- One user-session process containing the connection manager and per-Target-Device child ownership.
- `SMAppService.mainApp` for launch at login, with status inspection and a single System Settings recovery path when approval is required.
- Developer ID signing, Hardened Runtime, secure timestamps, no release `get-task-allow`, and notarization of the final distribution artifact.
- No root privilege, no LaunchDaemon, no privileged helper, and no broad process cleanup.
- Direct distribution for the private dogfood release; App Sandbox remains a compatibility spike before wider distribution.

### Add only if a later decision requires it

- An unprivileged LaunchAgent or LoginItem helper if the main app must stay alive after its UI quits or must receive launchd-managed restart behavior under an explicitly chosen job policy. Apple documents launchd as the manager of agents and documents `KeepAlive` as the property controlling whether a job is kept running; this is a separate lifecycle decision, not an automatic guarantee of the main-app login item. ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29))
- An XPC boundary if sandboxing or privilege separation proves necessary.
- A LaunchDaemon/privileged helper only for a specifically identified operation that cannot be performed as the logged-in user, with a separately reviewed minimal IPC surface.

## Decisions and limitations for the main agent to record

1. **Decision:** v1 is a single user-session menu-bar app registered with `SMAppService.mainApp`; do not create a LaunchAgent or privileged daemon solely for launch-at-login.
2. **Decision:** all shipped executable code is Developer ID signed, Hardened Runtime enabled, timestamped, and notarized; release artifacts do not carry `get-task-allow = true`.
3. **Decision:** relay and subprocess cleanup remains explicitly owned and per Target Device; cooperative `Process.terminate()` precedes any narrow PID-scoped fallback.
4. **Limitation/open decision:** `mainApp` documentation does not promise relaunch after an app crash. Decide separately whether crash recovery without a new login is required; if yes, prototype a user LaunchAgent/LoginItem helper before changing the boundary.
5. **Limitation/open decision:** App Sandbox compatibility for the current external-tool and listener model is unverified. Do not claim sandbox support until a focused build/runtime test proves the required entitlements.
6. **Limitation/open decision:** the current repository’s macOS 13 package declaration and macOS 26 `NWParameters.localEndpoint` requirement remain separate platform decisions; this ticket only establishes that `SMAppService` is available from macOS 13 onward.
